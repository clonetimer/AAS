# P3-C 第二批：任务失败诊断与安全恢复入口

日期：2026-11-06。目标是让普通用户在训练、评估、仅推理或服务重启失败后，能看懂失败发生在哪个阶段、受影响的对象、下一步应该做什么，并能从任务历史重新进入正确功能页。

## 用户与成功标准

用户主要是非程序员。失败信息应使用稳定错误代码、阶段名称、简明原因和可执行的下一步，不要求用户阅读 Python 异常栈。刷新或服务重启后，失败/中断任务仍可查询。用户不能误以为任务已自动恢复或继续执行。

## 当前依据

- `TaskRuntime` 已持久化训练任务的状态、进度、消息和结果摘要；重启时把 `running` 标记为 `interrupted`。
- 当前持久化不保留原始任务配置、遥测、模型对象或执行凭证，这是有意的隐私与一致性边界。
- `/api/train-status` 直接返回任务内部字典；没有最近任务历史 API。
- V2 训练已异步；有标签评估和无标签仅推理仍是同步 HTTP 操作，失败时只返回字符串错误。
- 归档失败与模型计算失败不同：训练/评估可能已经计算成功，但报告未完成归档。

## 设计选择与备选方案

### A. 结构化诊断 + 任务历史 + 手动重新提交（推荐）

在现有任务生命周期上增加阶段、错误代码、用户说明、恢复动作和最近任务查询；评估/仅推理的同步接口返回相同诊断结构。失败后回到对应功能页，由用户检查/修改输入后重新提交新任务。

优点：改动范围可控，继续保留当前安全边界；不会把旧请求、CSV 内容或凭证写入磁盘。代价：不支持从失败进程自动续跑。

### B. 将训练、评估、仅推理全部改为异步任务

统一任务状态和进度，体验最一致。代价：需重构评估 API、前端轮询、任务持久化和模型注册时序，当前阶段变更面过大。

### C. 持久化原始请求并自动重放

失败后可以一键重试。代价：会保存用户选择、数据引用及可能敏感配置；数据/模型可能已变化，盲目重放会产生不可审计结果。当前不采用。

## 本轮范围

1. 训练任务增加阶段字段：`queued`、`data_loading`、`algorithm_execution`、`model_validation`、`provenance_capture`、`report_archive`。
2. 失败诊断结构至少包括：`code`、`stage`、`stage_label`、`title`、`message`、`recovery_action`、`recovery_label`、`retryable`。
3. 常见原因可识别：输入文件/模型缺失、输入不合规、SQLite 锁/损坏、磁盘空间不足、目录权限、算法超时/内存上限/子进程异常、模型产物校验失败、来源证据失败、报告归档失败、服务重启中断。
4. `/api/train-status` 只返回公开状态投影，不暴露原始配置、内部异常、凭证或原始数据。
5. 新增 `/api/task-history`，按最近更新时间返回失败、中断及“计算完成但报告归档失败”的任务。
6. 训练页面展示阶段、原因和下一步；报告页展示最近失败/中断任务并可跳回训练/评估页面。
7. 有标签评估和仅推理同步接口在失败时返回同一诊断结构；归档失败作为“需处理事项”，不能误标为模型计算失败。

## 安全恢复规则

- 不自动恢复训练/评估进程，不复用旧的一次性执行凭证。
- 不在任务状态文件中持久化原始请求配置、CSV 行、遥测矩阵、模型对象、访问令牌或完整异常栈。
- “重新运行”意味着用户回到对应页面，核对数据和参数后创建新 task/run ID；不覆盖旧任务或旧实验。
- 仅提供安全的恢复导航和说明。本轮不提供自动重试、取消或归档凭证重放。
- 归档失败时，模型/计算结果仍按原有生命周期保留；报告未归档必须明确显示，不伪造成功报告。

## 非目标

- 不自动重启失败的算法子进程。
- 不改变模型训练/评估算法、指标或标签规则。
- 不持久化任务完整配置以支持无确认重放。
- 不实现长任务取消/暂停；归入后续 P3-D。
- 不承诺 Windows 实机验收；仍需现场运行。

## 验收

- 对同一异常类型，后端返回稳定错误代码和阶段，而不是依赖前端解析异常文本。
- 服务重启后，running 任务成为 interrupted，原因和恢复说明可查询。
- 任务历史只暴露安全字段，不含密码、文件绝对路径、请求配置、异常栈或执行凭证。
- 训练失败、评估输入失败、算法超时、磁盘不足和归档失败均能显示不同的用户动作。
- 报告页可见失败任务，能跳回运行页；页面文本使用安全 DOM API。
- 原有成功任务、实验归档、模型发布和监督指标行为不变。
