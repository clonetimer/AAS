# AAS V2 现场评估系统改造设计（执行基线）

依据用户确认执行的《AAS V2 智能故障检测算法评估系统改造评估方案 V1.1》（2026-11-05），结合 Phase 53 R7 Candidate / R3.9 源码快照实施。原现场包只读；改造维护独立本地 Git 功能分支。

## 用户目标与边界

- P0：训练/评估运行后自动形成可验证、可持久查询的报告；刷新和重启不丢已完成的结果。旧物理表 API 继续退役，不恢复 `/api/save-experiment` 的浏览器提交权限。
- P1-0：导入 CSV 即可预览/校验，数据身份治理与训练资格分层。
- P1-A：完整多列数据的帧区间多次故障注入、版本链、故障事件、全量 CSV/ZIP 导出。
- P1-B：训练支持本地 CSV；评估支持可信 AAS 模型包和 CSV；有标签评估与无标签评分分开。
- P2：历史库浏览减负、帧与时间视图、实验同条件比较、映射预设。
- P3：Windows 10/11、现场离线部署、备份恢复及性能 GUI 验收。

数据真实标签不得猜测，未经授权不得将本地 CSV 静默写入历史主库。训练/测试分组需防泄漏。任何预处理保留用户确认过的配置及质量标记，评估不能重新拟合训练期归一化。算法负责报警判决和后处理，平台只记录、展示和计算客观指标。任意外部 pickle/joblib 默认不可信，不可直接执行。

## 选定实施路径

采用先前评估的 **B：保留 V2 主库及算法内核，新增数据工作区、故障派生版本和实验自动归档**。与“各页面补按钮”相比，模型/数据契约保持一致；与全库重构相比，保留现场已有真实数据库和模型注册表。

### P0 数据与安全契约

服务端收到真实运行结果后，使用已存在的 `ExecutionRegistry` 固化的证据，自动归档到 `outputs/experiment_<id>/reports/`。写入 `summary.json`、`execution_result.json.gz`、`execution_config.json`，对完整输入快照在已有证据声明为完整时另写 `execution_inputs.json.gz`；可通过 `scripts/verify_experiment.py` 做本地 SHA-256 一致性校验。

训练使用服务端内部的 experiment_id（必须是受限安全字符）关联模型；每次评估有独立 run_id；归档路径不可覆写旧结果。归档失败须与算法执行成功区分，不能假报“报表完整”。列表默认查看全部任务，并可从运行页进入本次报表；只有模型注册记录、没有报告时明确解释，不生成虚假历史指标。

## 现有兼容风险

源码快照没有 `.git`，本次在独立复制目录创建本地基线 Git 仓库；非真实远端分支，不能假称已提交至 GitHub。基线单元测试发现 2 个旧物理表运行测试与正式 410 退役策略冲突；另有依赖 `torch` 的算法测试在当前缺少 PyTorch 的 Linux 环境失败。这些是实施前已观测到的基线，不作为本轮新增功能造成的回归。

## 迭代策略

先为 P0 编写详细执行计划并按 TDD 完成，保留已有接口；随后按 P1-0、P1-A、P1-B、P2、P3 分别写可验证的计划，逐段实现。是否具备 Stable 交付条件以 Windows 实机及离线全量验收为准，Linux 单测通过不代表现场验收。
